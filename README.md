# Pokémon TCG Pocket 交换与收藏

React + Vite 前端、Express 服务端、Supabase Auth/PostgreSQL。网站用于寻找交换伙伴与记录收藏，真实卡牌交换仍在游戏内完成。

## 本地运行

需要 Node.js 22+。推荐使用 npm：

```powershell
npm ci
Copy-Item .env.example .env
npm run dev
```

编辑 `.env`，填入自己的 Supabase 项目 URL 和 publishable key。不要把 `sb_secret_*` 或 service-role key 放进 `VITE_*` 变量。云端未配置时仍可本地维护收藏和使用本地识别，发布挂单与云端备份会显示不可用。

开发环境默认监听 `127.0.0.1:3000`。部署到容器时设置 `HOST=0.0.0.0` 和平台要求的 `PORT`。

## 数据库配置与升级

以项目维护者身份登录 Supabase Dashboard，在 SQL Editor 按顺序执行：

1. `supabase/migrations/202610080001_secure_trading.sql`
2. `supabase/migrations/202610080002_card_catalog.sql`
3. `supabase/migrations/202610080003_scan_quota.sql`

第一份脚本创建 v2 表、RLS 和受控 RPC，同时撤销旧 `trainer_backups`、`trade_listings`、`trade_proposals` 表的公开访问。**旧数据保留，旧客户端不能继续访问它们。** 不要同时继续提供旧版本网页，否则用户会碰到旧接口权限错误。已有正式站点应先进入维护状态，再完成脚本和新代码部署。

旧记录没有经过验证的账号 UUID，不能安全地仅凭好友码自动认领；旧引继码此前也由公开表返回过。用户可登录后在“收藏备份与恢复”明确合并此浏览器原有收藏，核对后备份到账号。仅在站点维护者独立核验归属后，才手动迁移云端旧备份。不要重新开放旧表或把好友码当登录身份。

邮箱登录使用 Supabase 默认的 Magic Link。在 Authentication > URL Configuration 配置正式站点的 Site URL 和允许的 Redirect URLs；开发时可加 `http://localhost:3000` 和 `http://127.0.0.1:3000`。生产环境配置自己的 SMTP。默认邮件点击链接即可登录；若使用验证码模板，需要包含 `{{ .Token }}`，页面也提供验证码输入框。

邮箱登录只验证网站账号，不证明该用户拥有其填写的游戏账号。

## 交换流程

- 访客可看公开大厅；发布、发送意向和备份需要登录。
- 发布时同时登记规范化的 16 位好友码，每侧最多 20 个候选卡，填写每张可出数量。
- 数据库检查卡牌目录及同稀有度，挂单有效期 7 天，每个账号最多 30 条有效挂单。
- 匹配提示只推荐伙伴；不会冒充对方生成交换意向。发送后由接收方接受，再进入游戏内交换。
- 接受时预约挂单内所选卡的数量；同一数量不能被其他意向重复预约。
- 双方分别确认游戏内已完成后，数据库原子扣减所选卡数量，保留其他候选卡和历史记录。重复确认不会再次扣减。
- 各端按已完成提案更新本地收藏，收藏与已应用提案 ID 在同一份快照中保存；云端备份包含这些 ID。若库存不足，显示核对提示而不虚构收卡。
- 备份使用版本比较：新设备应先读取并应用云端备份，再修改和保存。旧设备不能静默覆盖新备份。恢复前保留本地副本，可在备份弹窗重新读取。
- 账号之间的本地收藏、挂单、提案和备份版本分别保存；登录不会自动把另一个账号的收藏带入。

当前大厅分页读取最近 150 条活跃挂单；信箱分批读取参与者历史。页面在重新获得焦点和每 30 秒可见时刷新。大型市场仍需要后续增加服务端搜索及大厅分页入口。

## AI 与图片代理

设置服务端 `GEMINI_API_KEY` 后可启用云端识别；AI 请求验证登录 token 并消耗数据库配额：每账号每天最多 20 次、全站每天最多 500 次，按 UTC 日期重置。两步识别的每个云端请求各计一次，缓存命中和失败请求也计入额度。额度在数据库中，不随 Express 重启清空。

公开图片代理仅允许代码内列出的 HTTPS 卡图／头像域名；拒绝自定义端口、URL 凭据、重定向、非位图内容、超过 5 MB 的响应，并有 8 秒超时及 IP 限流。截图请求体有大小检查和 IP 限流。前置反向代理下默认不信任 `X-Forwarded-For`；如果需要精准按访客 IP 限流，应只对明确的代理网段配置 Express trust proxy，不可直接信任任意来源。

模型分数和图像匹配分数不是实测准确率，不再人为设定最低分数。无法定位的卡和无卡名的剪影不会按位置猜编号。云端 AI 模式失败时明确报错；两步识别失败后的本地匹配会显示提示。导入默认合并；替换数量也只修改已识别的卡，保留截图之外和未识别的收藏。导入要求核对截图结果，提供最近一次导入的撤销；后续收藏编辑或完成交换后撤销入口失效，以免覆盖新数据。

真实识别准确率仍需要用实际游戏截图验证，尤其是不同语言、三／五列布局、异画和数量角标。合成演示截图不能作为准确率依据。

可选 `KOFI_VERIFICATION_TOKEN` 用于验证 Ko-fi webhook。未经验证的回跳参数或训练家同名匹配不会授予勋章。公开感谢墙仅展示有效 webhook 的公开赞助，内存记录重启后消失；账号支付权益尚未实现。

## 规则维护

通用条件来源：[官方交换 FAQ](https://support.pokemon.com/hc/en-us/articles/34322874608660-Pok%C3%A9mon-TCG-Pocket-Trading-FAQ)。双方稀有度以及装饰、金框条件需要一致，具体可交换清单以游戏内 Detailed trade list 为准。

`src/data/tradeRulesConfig.json` 是本站开放范围。三星沉浸卡和 Promo 不开放，皇冠资格尚未核实，因此暂不开放皇冠挂单。更改规则或卡库后运行 `npm run catalog:seed`，审核生成的目录 SQL 并应用到数据库，确保客户端和数据库规则同步。

## 验证与生产构建

```powershell
npm test
npm run lint
npm run build
npm run test:http
```

数据库测试使用本地 PGlite PostgreSQL 验证真实 SQL、角色权限、单方／双方确认、预约数量、幂等和额度；不会读写正式 Supabase。HTTP 冒烟检查启动本地生产服务并在完成后结束进程。

部署前还应在独立测试 Supabase 项目用两个邮箱完成登录、挂单、接受、双方确认以及两台设备备份冲突测试。本地 PostgreSQL 测试不能替代真实 Auth、PostgREST 关系查询和 SMTP 联调。

生产启动：先构建，设置 `NODE_ENV=production`，再执行 `npm start`。`npm run preview` 仅预览静态前端，不提供 AI、代理与 webhook 接口。
